# Bevy Migration Audit

**Status:** analysis only. No gameplay, renderer, packaging, or asset-pipeline code is changed by this audit.  
**Reviewed:** 2026-10-22  
**Target:** replace the DriftEngine runtime with a native Rust application built on Bevy, prioritising Linux.  
**Estimated effort:** approximately **178–325 engineering person-days** for a careful full-feature migration and validation (roughly 9–16 full-time engineer-months for one experienced developer). This is an early planning estimate, not a commitment; the networking and rendering work have the widest uncertainty.

## 1. Executive assessment

This is a substantial port, not a dependency swap. The repository is currently a TypeScript application that runs in a browser/WebView and uses DriftEngine for its renderer, main loop, audio integration, input-related helpers, storage, and networking transport. Bevy is a native Rust ECS/game engine, so a native Bevy application needs Rust implementations of the simulation and presentation, plus native equivalents for the services that were previously provided by the browser and DriftEngine.

There is one valuable architectural advantage: **`src/sim/` is intentionally engine- and I/O-independent**. `tests/architecture.test.mjs` enforces this boundary. The existing simulation logic and tests are therefore the best specification for a Rust port, although TypeScript cannot simply be linked into Bevy as native Rust. The simulation should be ported with behaviour-preserving tests, not redesigned at the same time.

Recommended approach:

1. Keep the Node.js disc-reading, extraction, import, and optional remaster tools initially. They are an established content pipeline and do not need to be rewritten just to change the runtime.
2. Define and freeze the generated-asset contract, then build Rust loaders and validation for that contract.
3. Create a minimal Linux-first Bevy application and prove it can open a window, show a no-game-data screen, load synthetic test data, render one test fighter/stage, and exit in an automated smoke-test mode.
4. Port the simulation to Rust in small, testable slices while building the renderer separately.
5. Restore complete scenes, audio, modes, input, saves, and online play in stages. Do not make online play a prerequisite for the first playable offline build.
6. Only after the application has a stable no-ROM startup and a reliable native build, add the dedicated AppImage build and smoke-test workflow.

Bevy **0.20** was the current stable release at the time of this audit. Pin a specific Bevy release in `Cargo.toml`/the lockfile instead of targeting the moving main branch, and budget for its documented API changes when later upgrading. References: [Bevy 0.20 release notes](https://bevy.org/news/bevy-0-20/) and [Bevy repository / compatibility notes](https://github.com/bevyengine/bevy).

## 2. Repository inventory

The inspected repository has 411 tracked blob files, including 229 TypeScript source files and 77 test files. Approximate source sizes from the current tree:

| Area | Files | Source size | Migration implication |
| --- | ---: | ---: | --- |
| `src/sim/` | 97 | 1.30 MiB | The game rules and simulation; conceptually isolated, but substantial TypeScript-to-Rust work |
| `src/present/` | 71 | 0.79 MiB | Custom 2D/3D drawing, HUD, scenes, effects, character/stage rendering, and sound output |
| `src/app/` | 24 | 0.20 MiB | Browser lifecycle, 60 Hz loop, page integration, controls, settings, save I/O, camera, diagnostics |
| `src/assets/` | 24 | 0.11 MiB | Typed validation/loading of assets generated by the existing importer |
| `src/net/` | 7 | 0.09 MiB | Matchmaking/session protocol, snapshots, peer transport integration |
| `scripts/` | 84 | 0.62 MiB | Disc/arcade import, extraction, conversion, and asset-generation tools; retain initially |
| `server/` | 6 | 0.07 MiB | Node.js relay/server; potentially retain while replacing the native client transport |
| `tests/` | 77 | 0.52 MiB | Valuable regression coverage and architecture constraints |

These counts are file-size indicators, not a line-count or complexity metric. In particular, the cost of the 3D renderer and simulation is much higher than raw size suggests because correctness depends on frame timing, geometry, animation, rendering order, and comparison against the original game.

### Existing architecture worth preserving

- `scripts/`: understands the source disc/optional arcade dump and generates local runtime data.
- `src/assets/`: validates generated data before the game consumes it.
- `src/sim/`: deterministically advances fight/game state without importing DriftEngine or browser APIs.
- `src/present/`: translates state into graphics/audio through DriftEngine-specific APIs.
- `src/app/`: owns browser window integration, fixed-rate stepping, input, persistence and startup.
- `src/net/` and `server/`: online sessions and relay.
- `tests/`: unit/regression coverage, plus an architecture test that protects the simulation boundary.

The existing split is a strong starting point. Preserve the simulation/presentation boundary in the Rust design rather than mixing game rules directly into rendering systems.

## 3. What must change

### A. Application shell, frame loop, and platform services — medium/high

Current entry points are `src/main.ts`, `src/app/remake.ts`, `src/app/game.ts`, `src/app/quick.ts`, and `src/app/page.ts`. The page module creates the DriftEngine renderer and owns the canvas, asset fetches, fixed-step loop, quality management, error reporting, and browser-specific behaviour.

**Bevy replacement:** a Rust binary with Bevy plugins/resources/systems for startup, the window, fixed-step game advancement, asset readiness, pause/focus handling, diagnostics, and user-facing errors.

Keep the simulation's game field at exactly 60 Hz. Use a fixed-step accumulator / Bevy fixed schedule and test that render frame rate never changes the number or order of simulation steps. Rendering may interpolate, but must not mutate deterministic game state. Input must be sampled and queued at a well-defined point relative to each simulation step.

**Estimate:** 8–14 person-days for the initial shell, lifecycle, clock and diagnostics; some of this overlaps with the prototype.

### B. Simulation and game modes — very high

`src/sim/fight/`, `src/sim/game/`, `src/sim/math/`, `src/sim/data/`, `src/sim/effects/`, and `src/sim/sound/music.ts` contain extensive fighting and game-state logic: movement, collisions/hits, cancels, reactions, throws, camera choices, CPU behaviour, round/field sequencing, replay, menu progression, records, unlocks, Tekken Ball, Tekken Force, practice, and other game modes.

The simulation is deliberately free of the engine. However, its source is TypeScript, so Bevy cannot consume it directly as Rust code. Embedding a separate JavaScript runtime would add a second runtime, interop boundaries, packaging complexity, and harder deterministic debugging. **Recommended: port the simulation to Rust**, keeping explicit state-machine logic and fixed-point/integer operations wherever the existing behaviour depends on them. Do not blindly turn every simulation object into a Bevy ECS entity: ECS is useful for the presentation, while the original frame-step sequencing should remain explicit and testable.

Port each subsystem against the current JS implementation using deterministic fixtures and state/output comparisons. Start with integer/matrix math, input normalization, blank/default states, movement and poses, then hits/reactions/round flow, CPU, modes, records and replay.

**Estimate:** 40–70 person-days for the main simulation port and test adaptation. This is one of the largest estimates and should be revisited after a representative vertical slice.

### C. Asset pipeline and runtime asset format — medium/high

The existing `scripts/disc.mjs`, `scripts/extract.mjs`, `scripts/import.mjs`, `scripts/import/*`, and `scripts/lib/*` read locally supplied source data and generate typed assets in ignored/local directories. `src/assets/` validates JSON tables and a versioned manifest; the presentation loads custom fighter/stage/model/texture/audio formats.

**Recommendation:** retain the importer as a separate Node.js tool in the first migration. Document the generated files as a versioned interface, then implement Rust parsers/loaders for JSON, texture images and custom model/stage binaries. Add clear errors for missing data, wrong format versions, and incomplete imports. Only consider rewriting the importer after the Bevy runtime is playable; changing both sides of the asset contract simultaneously would make debugging unnecessarily difficult.

Never check in, upload, or bundle a user's disc image, arcade ROM/dump, extracted assets, converted content, screenshots, or app builds containing game content. Automated CI must use synthetic fixtures only.

**Estimate:** 10–18 person-days for a Rust runtime loader/validator and contract fixtures, excluding a full rewrite of the extraction/importer.

### D. 3D rendering, fighters, stages, camera and visual effects — very high

The major implementation is in `src/present/3d/`, especially `fight-view.ts`, `fighter/fighter.ts`, `stage/stage.ts`, `layout.ts`, `effects/*`, and stage/fighter helpers. This is more specialised than a typical Bevy scene: it includes custom model data, weighted CPU skinning and joint transforms, special face/hand/garment treatment, segmented/cullable stages, camera/projection rules, layered/translucent polygons, lighting, shadows, fog/backdrops, dynamic lights, particles, stage-specific drawing and remastered/arcade variants.

Bevy's built-in PBR renderer is not a drop-in equivalent for the game's specific drawing rules. Some content can use standard meshes/materials; other parts will need custom materials/shaders, explicit render ordering, geometry conversion, and visual comparison tests. The migration must establish coordinate/unit conversion, skeleton pose mapping, texture filtering and transparent geometry rules up front.

Suggested order: static test mesh + camera; one disc fighter; one stage; skinning/animation; depth/transparency and shadows; HUD composition; effects; special modes and arcade/remastered presentation. Keep a golden-image/manual comparison checklist for key states and multiple quality settings.

**Estimate:** 35–60 person-days for core 3D parity. Special stages, effects, arcade assets and remaster modes may push this higher.

### E. 2D scenes, menus, HUD, text, atlas and post-processing — high

`src/present/2d/`, `src/present/hud/`, and `src/present/scenes/` currently paint the title/menus, character select, versus/results/options screens, HUD, control glyphs, fonts, portraits and overlays through DriftEngine's 2D APIs and custom atlas/light layers. These screens encode a lot of layout and transition behaviour; they are not just decorative UI.

Use Bevy UI for conventional menus/settings where it matches the required behaviour. Use custom 2D meshes/sprites and render layers for pixel-controlled screens, HUD elements, effects and the game's ordered composition. Recreate CRT/filter/post-processing only after the normal render path is stable. Keep presentation state derived from game state; do not duplicate game rules in the UI.

**Estimate:** 25–45 person-days for the major scenes/HUD and visual parity.

### F. Audio, music, voices, effects, and movies — high

`src/present/sound/` has a custom mixer and playback pipeline, including a worklet (`processor.ts`), timed sound commands, voices, music tables, XA songs/tracks, sample handling and buffering. This is not a simple collection of audio files. `src/app/sound.ts` also depends on browser audio startup rules. Movies are currently supported as web media where extraction tools are available.

Bevy's standard audio playback is not a direct replacement for the custom mixer. Plan a native audio output backend and a Rust port of the timing/mixing logic (with dedicated tests for command order, sample rates, loop positions and silence/underrun behaviour). Decide whether to use a low-level output library or a Bevy integration after the first prototype. Native movie playback is a separate investigation; the first playable slice can report unsupported/missing movies cleanly rather than blocking combat.

**Estimate:** 15–30 person-days for sound parity and a first decision/implementation for movies. Movie playback or audio fidelity complications may increase this.

### G. Controls, settings, saves, window behaviour and accessibility — medium

Browser key/gamepad handling, touch support, settings, fullscreen, vibration/rumble, FPS/quality controls, persistent progress and crash handling live primarily in `src/app/`. Linux priority means keyboard, common gamepads, window focus/fullscreen, resolution, audio device behaviour, save persistence and clean error messages must be validated on Linux first. Touch support can be deferred if the immediate target is a desktop AppImage.

Use Bevy input/window APIs where adequate, Rust-side settings/storage, and an explicit migration or reset policy for old browser save data (there may be no useful shared data path between the native app and browser storage). Do not silently overwrite or misinterpret saves.

**Estimate:** 10–18 person-days.

### H. Online play and networking — high risk; schedule after local offline parity

`src/net/` and `src/app/online.ts` use DriftEngine's network transport and browser peer-connection facilities alongside the Node relay in `server/`. The relay may be reusable, but a native Bevy client needs replacement WebSocket/session transport and a decision for direct peer connectivity. Browser WebRTC APIs are not automatically available in a native Rust binary.

Keep the application protocol and compatibility/version checks stable wherever possible. First establish two local offline players/CPU and reliable deterministic replays. Then evaluate native WebRTC support versus an alternative relay-mediated transport; changing NAT traversal or wire protocol has compatibility and hosting consequences. Include reconnect, timeout, desync, waiting-room and version-mismatch tests.

**Estimate:** 20–40 person-days. This assumes the existing protocol/server can largely be preserved; native peer transport or protocol redesign could exceed the range.

### I. Linux release and AppImage CI — later milestone, not part of this audit implementation

The current `scripts/app.mjs` delegates desktop packaging to the DriftEngine packager, and the app's present startup assumes generated game data can be loaded. Both assumptions need to change for a native Bevy binary.

The later Linux workflow should:

- Build a pinned Rust/Bevy release on a documented Ubuntu runner and cache Cargo downloads/build outputs.
- Package a Linux x86_64 AppImage without any game ROM, disc image, dump or converted game content.
- Provide a deliberate first-run/no-data screen with clear instructions, instead of treating missing ROM-derived files as a generic fatal crash.
- Add a smoke-test mode that starts the AppImage without a ROM, initialises the window/render path, verifies the expected no-data state, and exits with a machine-checkable success/failure result.
- Run the smoke test in CI with a software-rendering/virtual-display setup where available; collect logs and fail on panic, loader errors or missing required runtime libraries.
- Upload the AppImage as a workflow artifact. Release publication should be a separate, explicit workflow after the artifact and smoke test pass.
- Keep the CI fixture data synthetic and ensure artifact contents are audited. The user can then test the AppImage locally with their own content, which CI must never receive.

The no-ROM smoke test can prove packaging/startup and the missing-content path; it cannot prove that the game renders or plays correctly with real disc data.

**Estimate:** 8–15 person-days once the Rust application builds reliably. The broader CI/release/performance validation is included in the totals below.

## 4. Effort estimate

These estimates assume a developer experienced in Rust/Bevy and comfortable with reverse-engineered rendering/audio behaviour, full-time work, preservation of existing game features, and careful regression testing. They do not include new gameplay features.

| Work package | Low | High |
| --- | ---: | ---: |
| App shell, fixed-step loop and diagnostics | 8 days | 14 days |
| Rust asset loaders and contract validation | 10 days | 18 days |
| Simulation port and regression tests | 40 days | 70 days |
| 3D rendering, fighters, stages and effects | 35 days | 60 days |
| 2D menus, scenes, HUD and effects | 25 days | 45 days |
| Audio/music and initial movie strategy | 15 days | 30 days |
| Input, settings, saves and platform lifecycle | 10 days | 18 days |
| Online transport/client migration | 20 days | 40 days |
| Integration, parity/performance testing, Linux packaging/AppImage CI | 15 days | 30 days |
| **Total** | **178 days** | **325 days** |

At 20 working days per month, that corresponds to roughly **9–16 full-time engineer-months**. A single developer's calendar duration can be longer because rendering, simulation and transport work have sequential dependencies. A reduced offline-only version that defers online play, movies and some optional presentation modes can land earlier, but should be treated as a distinct target rather than full parity.

Confidence is medium-low until a vertical slice has validated model loading, animation, stage rendering and a fixed-step Rust simulation. The largest uncertainty is exact visual/behavioural fidelity, followed by native online peer connectivity and the custom audio pipeline.

## 5. Proposed milestones and gates

### Milestone 0 — architecture and parity plan
- Agree on the target feature set and explicitly defer online play for the first offline milestone.
- Record current behaviour for one fighter, one stage, one round, input, pause/restart, KO and round transition.
- Freeze the generated asset manifest/schema and create synthetic test fixtures.
- Choose a pinned stable Bevy release, Rust toolchain, Linux runner and license-compatible dependencies.

**Exit gate:** design decisions and test fixtures reviewed; no existing functionality removed yet.

### Milestone 1 — Linux-native proof of concept
- Create a Cargo workspace/app using Bevy; open a window and draw a test scene.
- Implement a 60 Hz fixed-step harness and keyboard/gamepad input diagnostics.
- Implement a no-ROM/no-assets startup state and `--smoke-test` mode.
- Load one synthetic/custom model and stage fixture through Rust; establish a frame capture/reference checklist.

**Exit gate:** reproducible `cargo test` and release build on Linux; smoke test succeeds without game data; no copyrighted data is required.

### Milestone 2 — assets and offline vertical slice
- Implement validated runtime loading of manifest, data tables, textures and model/stage formats.
- Port math, skeleton, movement, input, hits, reactions, round progression and a minimal offline match to Rust.
- Render one fighter on one stage with basic animation, camera, hit feedback and minimal HUD.
- Compare selected state traces against the TypeScript reference.

**Exit gate:** one local offline round can be started, played and completed with deterministic results; test fixtures and failure messages are reliable.

### Milestone 3 — game and presentation parity
- Port remaining simulation/modes, menus/select/versus/results/options, save/settings, quality modes, complete character/stage handling and visual effects.
- Port the custom sound/music mixer and restore movie behaviour where viable.
- Run the full fixture/regression set; measure frame-time and memory use on Linux.

**Exit gate:** agreed offline feature list passes; rendering/audio gaps are documented rather than hidden.

### Milestone 4 — networking and release hardening
- Implement native online transport; verify two-client match compatibility and reconnect/failure paths.
- Add Linux AppImage creation, no-ROM smoke test and artifact upload; later add explicit release publication.
- Verify that CI artifacts contain no user-provided game data and test the AppImage on a clean Linux environment.

**Exit gate:** CI can build and launch the ROM-free AppImage consistently; local content setup remains user-controlled.

## 6. Main risks and mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Visual mismatch caused by Bevy's different render pipeline | High | Build a fighter/stage prototype early; test custom material/render ordering before porting all assets |
| Simulation drift during TS-to-Rust conversion | High | Preserve frame sequencing/integer semantics; create replayable input traces and compare state snapshots |
| Browser-only WebRTC/network assumptions | High | Defer online until offline parity; prototype native peer transport as a separate spike |
| Custom audio/mixer timing does not map to standard Bevy audio | High | Port mixer independently and test sample timing/loops before integrating the full game |
| Asset importer and runtime schema change at once | High | Keep importer initially and version the generated-asset contract |
| CI accidentally bundles user content | Critical | Synthetic fixtures only, ignored local data directories, and artifact content checks |
| Bevy API churn while migration is underway | Medium | Pin Bevy and Rust versions; upgrade only in deliberate maintenance changes |

## 7. Decisions recommended before implementation

1. **Target:** native Rust/Bevy desktop first; Linux x86_64 is the first supported platform. Other targets can follow after Linux stability.
2. **Simulation:** port `src/sim/` to Rust; do not embed a JavaScript engine unless the prototype identifies a compelling, measured reason to do so.
3. **Importers:** retain Node.js scripts at first; only the runtime and required platform services move to Rust/Bevy in the initial phases.
4. **Gameplay scope:** offline gameplay and gamepad/keyboard handling first; online play, mobile/touch targets, and optional remaster features follow.
5. **Asset policy:** the repository and CI never contain the user's disc/ROM/dump or converted game content. The first-run experience must work without it.
6. **Release workflow:** design it now, implement it only after the no-ROM native app and build are stable.

## Conclusion

The migration is technically feasible, and the engine-independent simulation boundary lowers the risk, but a full native port with game parity is a multi-month project. The safest first implementation is a Linux-first Bevy proof of concept with synthetic assets and a no-ROM smoke-test mode, followed by an offline vertical slice. Do not start by rewriting every subsystem at once, and do not build the AppImage release workflow before the underlying native startup path is stable.
